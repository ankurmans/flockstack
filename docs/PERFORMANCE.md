# Performance: what makes a request slow, how to measure it, what keeps it fast

FlockStack Cloud runs on Cloudflare Workers. A request is slow for one of four reasons, in this order of how often they were the cause:

1. **The Worker's script was not loaded.** A new isolate loads the whole script before it answers anything, and Cloudflare starts new isolates all the time at our traffic. The app's script was 40 MB (63 MB before the first speed work; it is 28 MB now): a cold request cost 1.5 to 4 seconds of which almost none was the page. Loading costs roughly 30 ms per megabyte, and evaluating the modules of what the request uses comes on top.
2. **The code the request evaluates.** Module top levels run on the first request of a route: the 230 actions' zod schemas, Better Auth with its plugins and its signing code, the AWS clients. They run once per isolate, so they are a cold-start cost and nothing after.
3. **Round trips to the database.** Every call to D1 is a hop, and a dashboard page is a chain of them (`tests/query-budget.test.mjs` counts them). Rows read and bytes read matter too.
4. **Work the page does for nobody.** Reading every issue a newsletter ever sent, with its body, to show five.

The app Worker is split so that most requests never pay 1 and 2: the router and the public pages Worker start in milliseconds, `/api/v1`, `/mcp` and the OAuth endpoints are served by the lean API Worker (`workers/api`, 7.9 MB), and what readers' mail clients send by themselves (the open pixel, the click redirect, unsubscribe, the archive's beacons, the signup forms' address) by the readers Worker (`workers/readers`, 2.2 MB). `docs/ARCHITECTURE-WORKERS.md` has the picture.

## Budgets

`perf-budgets.json` holds the sizes the scripts must stay under: the app's `handler.mjs` and the script Wrangler uploads, the API Worker, the readers Worker, the router and the public pages Worker. `node scripts/perf-budget.mjs` (`npm run perf:budget`) prints them and exits 1 when one is over; `scripts/deploy-all.mjs` runs it after building and before anything is changed (`--require-app`); `tests/perf-budget.test.mjs` runs it on every `npm test` that has a build. A budget is raised only in a change that says why a Worker had to grow, and the change should say what it bought.

When a budget fails, find what grew: for the app, `.open-next/server-functions/default/handler.mjs.meta.json` (esbuild's metafile, inputs by chunk file) and `node scripts/dedupe-chunks.mjs` output in the build log (Turbopack writes the same chunk under several names; the build keeps one, `open-next.config.ts`); for the API and readers Workers, `node scripts/build-api-worker.mjs --metafile` and `node scripts/build-readers-worker.mjs --metafile` write `workers/api/dist/index.js.meta.json` and `workers/readers/dist/index.js.meta.json`.

## Headers that tell where time went

Every response carries `server-timing` and `x-served-by`. Through the router: `router;dur=` is the whole time in the router, `app;dur=` or `api;dur=` is the Worker's own handler (from the request reaching its code, so without starting its isolate) and `app-wait;dur=` or `api-wait;dur=` is how long the router waited for the Worker. The gap between the wait and the handler is the isolate: a cold start, or queueing. `x-served-by` is `router`, `website`, `public`, `api` or `app`.

## What a request evaluates: two tools

- `node scripts/route-weights.mjs` reads the build and says, for each class of route (dashboard, reader pages, API, system, public), how much of the handler its routes list (`R.c("server/chunks/...")` in each route's entry, sizes from esbuild's metafile). On the 2026-10-23 build the handler was 27.7 MB: 11.5 MB listed by some route, 3.6 MB the Next.js runtime, 1.1 MB route entries and manifests, and the rest chunks that load on demand. A class's routes share most of it, which is why splitting traffic into Workers by class helps with *what is served*, not with how big the app is: the dashboard's pages alone list 5.9 MB of the 11.5, but the app's single script carries all of it.
- `node scripts/page-closure.mjs "app/(app)/contacts/page.js"` lists the packages a page imports statically (what its first request evaluates before answering) and, with `--why`, the chain that brings one in. `tests/dashboard-weight.test.mjs` runs it on the pages everybody opens and fails if one of them imports an SDK, the action schemas or the OAuth provider. Before 2026-10-23 the dashboard layout imported 2.1 MB: the AWS SES SDK (through `lib/ses.js`, imported by the sign-in code), Upstash's clients, Markdown, and the contacts page the whole action registry with zod (through a docs example) and Stripe (through the billing provider). Now it imports 1.2 MB, and those load when the code that uses them runs (`import()` inside `lib/ses.js`, `lib/image-storage.js`, `lib/rate-limit.js`, `lib/send-rate.js`, `lib/sending.js`, `lib/billing-provider.js`; `lib/segment-schema.js` and `lib/actions/cursor.js` split out of modules whose other half every page needs).

**Lazy is not smaller.** The handler did not shrink: it grew from 27.7 to 28.3 MB, because every `import()` is a chunk of its own, in each of Next.js's two layers (server components and SSR) that reach it. What laziness removes is the evaluation of code a request never uses, not its bytes. The remaining weight is the framework twice (Next.js 3.3 MB of source in the server layer and 4.9 in the SSR layer), Better Auth and its OAuth provider (3 MB), mingo (1.8), zod (2), the MCP SDK (1), the editor (0.9, only its two pages load it) and the long flat tail. Getting the script under 18 MB means dropping routes from the Cloud app, not deferring them: the API, MCP and OAuth routes, the docs and the reader pages are copies kept so that rolling back is a switch. A second app Worker for the dashboard alone, built from the same repository with those routes left out, is the next step; it is a change of what the router can fall back to, which is why it was not made here.

**What the middleware loaded.** `proxy.js` runs before every request and is bundled into the middleware (2.9 MB, evaluated at start). It imported the document store, mingo and the models for two lookups that only a newsletter's host needs (`lib/host-routing.js`, `lib/redirect-routing.js`); they load with the first such lookup now (`tests/proxy-imports.test.mjs`).

## Cold start of the app, and a warm-up that did not work

A request to an isolate that has answered nothing costs script load plus the first evaluation of Next.js and the route. Measured locally with `wrangler dev --local --host localhost` and a fresh process per sample (the cold request is the first one the process answers; `--host localhost` because Wrangler otherwise gives the Worker the host of its first route, which the proxy takes for a newsletter's): `/signin` 650 ms, an authenticated overview 870 ms, campaigns 850 ms, contacts 960 ms; after one `GET /api/health` the first authenticated page took 340 to 360 ms, after `/api/health` and `/signin` 220 to 310 ms. About 60 percent of a dashboard page's cold start is the app starting, whatever the page.

**The router warming the app did not work on the platform, so it is not in the code.** The idea: a visit to a docs page (a request the router answers from PUBLIC) asks the app, behind the response, for `/api/health` and `/signin`, so the sign-in and dashboard that follow find it loaded. On a throwaway stack (router, a hello Worker as PUBLIC, the app, a throwaway D1; a redeploy before each sample, the visitor reading `/docs` and then waiting 8 s on the same connection) the first authenticated request after the warm-up was still cold in 3 of 4 rounds for sign-in (87 ms once, then 1.2 to 2.1 s), 4 of 4 for the overview (1.7 to 2.5 s), 3 of 4 for campaigns (497 ms once), and asking four times at once (`WARM_FANOUT`) changed nothing (sign-in 1 of 4, overview 0 of 4). `wrangler tail` showed the warm-up requests reaching the app (cpu 180 to 410 ms, wall 190 to 420 ms), so they ran; the visitor's request went to another machine of the data center, which has its own isolates and loads the 28 MB script itself. The same shows in the "warm" requests of the plain measurements below: right after a deploy, a second request on a new connection was often as slow as the first. So a warm-up from inside the data center cannot be relied on to reach the machine a visitor's next request lands on; the cold start has to be made smaller, not hidden.

## Measuring a cold start

Browsers and `curl` from one laptop cannot tell a cold request from a warm one; the Worker has to say. The technique, which `docs`-less scripts in someone's scratch directory used for every number in this repository's speed reports:

1. **Stamp the isolate.** Wrap a copy of the Worker's script so that every response carries `x-isolate-id` (a random id made on the first request of the isolate), `x-isolate-n` (how many requests that isolate has answered) and `x-handler-ms`. `n=1` is a request that started its isolate: cold. The wrapper is a few lines around the default export (`const stamped = { ...worker, async fetch(request, env, ctx) { ... } }`); it is for a throwaway build only, never committed. A random id cannot be made in the global scope of a Worker, so it is made inside `fetch`.
2. **Deploy it as a throwaway Worker** named `flockstack-speed-*`, `workers_dev` only, no routes, crons or custom domains, bound to the same D1 (read-only use: GETs that do not write) with throwaway secrets, and delete it after (`npx wrangler delete --name <name>`). Never measure on `flockstack` or `flockstack-eu`. Better Auth's first use of a host inserts one row in the `oauthResource` collection (`/.well-known/oauth-protected-resource`), and `/api/auth/jwks` creates a signing key when there is none, **encrypted with the throwaway's secret**: do not request `/api/auth/jwks` against a database that belongs to anything real.
3. **Get cold requests on purpose.** Isolates idle out after minutes and the pool is shared, so waiting is slow. A redeploy (`wrangler deploy --var CHURN:<time>`) throws the isolates away: send a burst of requests (one per route, all at once) 2 seconds after it, then the same burst 4 seconds later for the warm ones. Repeat for a few rounds. Classify by `x-isolate-n`: `1` cold; an isolate and route seen before, warm; the rest are the first request of a route in a warm isolate, which still evaluates that route's modules.
4. **Time the requests the way a client does:** `curl -w '%{time_starttransfer} %{time_appconnect}'` and take the difference (first byte minus the TLS handshake), from the same machine at the same time for the Worker and for a Worker that returns "ok", which is the floor (60 to 120 ms here). Report medians of many.
5. **CPU and wall time of the invocation:** `npx wrangler tail <name> --format json` prints `cpuTime` and `wallTime` for each request. Join them to your requests by time: the cold ones are the ones with `x-isolate-n: 1`. The platform's CPU on a cold request is about twice a laptop's.
6. **Locally, with less noise:** `npx wrangler dev --local --config <config> --persist-to <dir outside the config's folder>` runs the same workerd; changing the script file reloads it (a new isolate), and the first request after the reload is a cold one. Do this with a database seeded by `tests/helpers` to measure authenticated routes. Local numbers are about half the platform's.

## The database

`tests/query-budget.test.mjs` renders the dashboard's busiest pages inside their layout, as a signed-in visit, and counts what they ask the driver (`setQueryObserver` in `lib/docdb/driver.js`: one event per call, with the statement, its parameters, how many statements, how many rows were read). The budgets are the round trips and rows of each page today with a little room, and the same test asks SQLite (`scripts/explain-queries.mjs`, on a database built from `migrations/` as D1's is) whether any statement a page ran reads a table whole. `tests/send-budget.test.mjs` does the same for starting a send and for a batch of messages (round trips per message, which must not grow with the list).

`FLOCKSTACK_SQL_LOG=/tmp/sql.jsonl npm test` writes every distinct statement the whole suite ran; `node scripts/explain-queries.mjs /tmp/sql.jsonl` reports which of them read a collection's table whole, on that migrated schema. A table that has a few rows for ever may be fine; one that grows with customers, readers or sends needs an index in a new migration (`CREATE INDEX IF NOT EXISTS`; D1 only has what the migrations made).

What the audit found and what changed is in the commit messages of `perf/speed-2`; the standing rules are:

- **Ask for the fields a page shows.** `select(...)`, `exists`, `distinct` and an aggregate that starts with a `$match` and a `$project` of plain fields have SQLite hand over just those fields (`lib/docdb/model.js`, `selectedColumns`). A campaign carries its HTML (up to 200 KB), so a list of 300 of them used to read tens of megabytes to draw a table.
- **Bound the window in the first `$match`.** `getEmailStats` read every issue the newsletter ever sent to keep the last 60 days of them.
- **Run independent reads together** (`Promise.all`), and ask for the same thing once per request (`React.cache` in `lib/auth.js`, `lib/selected-newsletter.js`).
- **Reads asked for together are one round trip** (`coalescingDriver` in `lib/docdb/driver.js`, wrapped around the D1 driver). A dashboard page asks for twenty things in one `Promise.all` and D1 answers a Worker's parallel calls a few at a time. Measured from a Worker in Madrid on a throwaway D1 (primary in Western Europe): one statement 6 to 13 ms, twenty-two in parallel 43 to 49 ms, the same twenty-two as one `batch()` 12 to 15 ms; the gap grows with the distance to the primary, which is where a US visitor is. The statements of one turn of the event loop (a `setTimeout(0)`) go as one batch; a lone read, a write or anything that is not a plain `SELECT` goes at once; a batch that fails is run again statement by statement so that each caller gets its own error. Round trips per page went from 22, 15, 22, 19 and 13 (overview, campaigns, contacts, reports, segments) to 6, 6, 6, 6 and 4, carrying the same statements.
- **The chain every page starts with is two deep, not three.** Better Auth reads the session and then the user; the account was read after that. `getCurrentAccount` (`lib/auth.js`) now reads the account from the session token while Better Auth validates the session (`findAccountBySessionToken`) and uses it only if the session's user owns it. The overview also asks for all its sections as soon as it knows the newsletter, instead of one round trip later when React reaches each section. Depth (the longest chain of dependent round trips, measured with a simulated 100 ms latency): overview 6 to 5, campaigns 6 to 5, contacts 5 to 4, reports 6 to 5, segments 5 to 4. `tests/query-budget.test.mjs` counts round trips, statements and rows per page, and runs the pages through `coalescingDriver` as production does.
- **Indexes.** The statements of the whole suite, run through `scripts/explain-queries.mjs`, read these tables whole: the OAuth clients' `clientId` lookups (every token request), now indexed by `migrations/0027_oauth_client_lookup.sql`; the rest are admin pages, a cleanup and tables that hold a few rows for ever.
- **Every update is a read and a write** in the document layer (an optimistic compare-and-set), so an update costs two round trips: a loop of updates per message is the send path's cost (about 10 round trips per message). A single-statement `UPDATE ... json_set(...)` for `$set` and `$inc` of plain paths would halve it; it was not done because the semantics of casting, timestamps and unique indexes live in the JavaScript path.

### D1 read replication

D1 can serve reads from replicas close to the visitor (the Sessions API, `env.DB.withSession(...)`). It was **not enabled**; this is what it would take and what it risks.

- **Where.** `lib/docdb/driver.js` `d1Driver` talks to the binding through `binding.prepare(...)` and `binding.batch(...)`; with replication on it would talk to a session (`session = binding.withSession(bookmark)`; `session.prepare(...)`, `session.batch(...)`). The session must be per request, while the driver is per isolate, so it needs request-scoped storage: an `AsyncLocalStorage` started in `worker-entry.mjs` (app) and `workers/api/index.js` (API), around the handler, holding the session. `lib/docdb/driver.js` `getDriver` is the only place that builds the driver.
- **Consistency.** A session gives sequential consistency: within it, reads see its earlier writes and never go back in time, provided each request passes along the bookmark of the last (`session.getBookmark()`). Between requests the bookmark has to travel with the visitor: a cookie for the dashboard (sign in writes a session row, and the next request is a read that must see it, or the visitor lands on the sign-in page again), a header for API clients (`x-d1-bookmark` in the response and the next request), which API clients and MCP clients do not know to send, so a `POST` followed by a `GET` from a script could miss its own write. That is a behavior change for API consumers, which is why the API Worker should stay on the primary (`withSession("first-primary")`) for anything that carries an API key or an OAuth token, and replicas would serve only requests with a bookmark cookie, public pages and archives.
- **Webhooks, QStash jobs, crons, sends** must read the primary: they read what they or another job just wrote, with no visitor to carry a bookmark.
- **What it would buy.** The US database's primary is in Western Europe (`served_by_region: WEUR` for `flockstack`, whatever the visitor's continent), so a US visitor's page pays an ocean for each of its 14 to 35 round trips; replicas would take the reads to the visitor's region. The EU database is jurisdiction-restricted to the EU, where the visitors and the primary are already close. It is the biggest remaining gain for US dashboards, and the part that needs care is the bookmark; the flag it would sit behind is `D1_READ_REPLICAS=true`.

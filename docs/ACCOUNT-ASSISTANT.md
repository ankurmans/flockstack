# Account assistant

Open **Account assistant** in the dashboard or press Cmd+J (Ctrl+J). It works on the selected newsletter. This version is owner-only: team seats, including admins, cannot create or use an owner's grant. Reading the page neither creates a grant nor calls a model.

Choose read only, write drafts, or sends with approval, then explicitly create a grant. It is a real account-owned API-key record marked `purpose: assistant`, limited to one newsletter and 100 tool calls a UTC day, expiring in 90 days. It has a random nonrecoverable hash and no generated or exposed bearer credential. Even a matching hash cannot authenticate a public request for this record. The API keys page identifies and revokes it; it shares the existing 20-active-key limit. Revoked and expired grants stay invalid and are never recreated by chat.

After separate consent, the assistant can read the selected newsletter's writing brief and aggregate recent issue results, list/read campaigns, check readiness, create and edit Markdown drafts, save simple status/tier/engagement segments, read the editorial plan and create planned newsletter/LinkedIn items. It cannot inspect contact records or sender details, manage keys, billing, payments, teams, exports or webhook secrets, approve requests, publish LinkedIn posts, or use arbitrary tools or addresses. These eleven tools are an explicit subset of the action registry; the assistant is not the docs-only support chat.

Every tool goes through `runAction` with the actual persisted grant, account and signed-in owner. Current account state, ownership, grant revocation, expiry, level and newsletter are checked again before each inference and tool. Existing agent guards enforce scope, caps, target ownership and draft-only edits; scheduled copy cannot be edited. `send_campaign` and `schedule_campaign` always produce the normal approval request on a sends-with-approval grant; lower grants refuse them. The owner must review and decide it on Approvals. Execution resolves the same real grant again and refuses a revoked actor. No artificial key or dashboard-handler bypass is used.

Each user turn has at most three Workers AI model invocations and four serial tool attempts. Every started inference, including a failure or malformed answer, consumes the existing shared daily AI allowance. The account also has a 30-turn-per-hour action limit. No automatic model fallback or whole-turn retry runs. Identical tool arguments within a turn reuse the result; draft and plan creation use stable keys derived from the supplied turn ID and tool position. This is not a transaction or a complete conversation-replay guarantee: a differently planned retry can take different actions, and segment creation uses its ordinary unique name. Review activity and approvals after an interrupted request.

Tool cards report actual completed, refused or approval-required results. If a model fails after a draft tool, its completed card remains in the response. Model prose can be wrong; it never establishes delivery. Pending-send responses are worded by the server as awaiting approval. A planned day is editorial intent and never schedules or publishes anything. Clearing the conversation does not undo actions.

Cloudflare-hosted Qwen3 30B runs through the existing Workers AI binding and AI Gateway, with gateway logging and caching off. The owner explicitly consents to global processing of the conversation and selected private brief, authored draft and bounded tool DTOs. The server adds no contact records, sender addresses, billing/credential data or private editorial notes. The owner must avoid including these in chat or authored source text. Tool errors send only bounded codes, and every allowed tool has an explicit projection; authored copy and entries can be truncated with an explicit flag. No provider exception body or prompt is logged.

Only recent plain user/assistant text may come from the client; system/tool roles and extra history fields are rejected. Server tool calls are parsed against strict schemas and a fixed allowlist. Draft/brief text is untrusted material. Prompt instructions are not a security boundary: the persisted grant and server checks enforce permissions even if the model follows hostile text.

No server chat transcript, local storage or chat cookie is added. Recent conversation is tab memory and clears on reload, navigation away or clearing it. Grants, daily counters, ordinary drafts/plans/segments, activity logs and approval records retain their existing lifecycle. `assistant-grants.csv` includes owned grant metadata without hashes; account purge removes grants with other keys. Started model attempts share the existing two-week AI counter retention.

Self-hosting uses the existing Workers AI binding and `AI_DAILY_LIMIT`; an absent limit means no daily AI cap, while turn/hour and tool/grant limits still apply. Tests use a fake binding and synthetic accounts, including real approval execution against stub jobs. They do not establish live model availability, tool-selection quality, latency or operational billing. No live model work is performed as part of this build.

Provider references: [Qwen3 on Workers AI](https://developers.cloudflare.com/workers-ai/models/qwen3-30b-a3b-fp8/) and [Cloudflare function calling](https://developers.cloudflare.com/workers-ai/features/function-calling/).

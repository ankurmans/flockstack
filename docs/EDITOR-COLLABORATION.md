# Realtime editor and private discussion

Optional, off by default. On a rich-text draft, **Edit together and discuss privately** opens the shared editor after the ordinary draft saves. The subject, preview and actual Tiptap document use Yjs, with live carets and named presence. Concurrent edits merge; reconnect sends only local changes the saved document has not confirmed. No document is persisted to browser localStorage. If access or the saved document changes, editing stops and the local-copy control preserves the visible text for manual recovery. **Save and return to issue** waits for a durable checkpoint; delivery and approval still happen through the existing issue flow.

Viewers read. Active editors and admins write. Every update, cursor/heartbeat and broadcast recipient checks the current sign-in session, account/team membership and draft state through a service-binding-only API authority. Revoked sessions or seats, a different account, and scheduled/sent/canceled issues cannot continue. The 60-second app-key-derived ticket travels in a WebSocket subprotocol, never the URL; cookies and bearer tickets are not stored in Durable Object attachments. Public request identity headers are discarded.

One SQLite Durable Object coordinates an account/campaign. EU namespaces use `jurisdiction("eu")` before object names. Updates enter a serial queue. The server applies the Yjs update to a copy, validates the shared editor schema and serializes its HTML itself. A compare-and-set checkpoint must match the exact prior draft content and status. REST edits, restores and send transitions stop stale rooms. An outside edit or restore also changes an edit identifier, so an identical-text restore still invalidates the old room. The saved subject and preview use the existing trim rules while the CRDT edit buffer preserves spaces during typing. Ordinary editor autosaves now carry the same content precondition. The CRDT state and canonical HTML are persisted before acknowledgement/broadcast; D1 snapshots recover a lost object. Unknown acknowledgements are reconciled using Yjs snapshots/state vectors, including delete metadata.

Bounds: 20 connections per issue, 128,000 bytes per client update, 1,000,000 UTF-8 body bytes, 200-character subject and 300-character preview, 2,000,000-byte CRDT state, 40 pending room operations and 60 messages per connection per second. An oversized single change stops with a local-copy instruction rather than overwriting the saved draft. The normal editor remains available.

Private threads have plain text, selected-text quotes and Yjs relative anchors, replies, resolution and active-collaborator mentions. Quotes can locate the selected text after concurrent edits; a different document epoch marks old anchors outdated. They never enter public comments or subscriber emails. Mentions are visible in the private editor and send no email. Collaborator pickers show user IDs/public display names, never sign-in emails; revoked and pending seats are absent. A thread has at most 50 replies and an issue at most 100 threads; reads page by 20. Removal clears its discussion text, replies and mentions. Deletion permissions still follow the action scopes and team role.

Private account exports include `editor-collaboration.csv` and `editor-threads.csv`. CRDT state can contain earlier deleted text. The hourly cleanup removes up to 100 snapshots whose last checkpoint is older than 30 days, removing object copies first and rechecking the checkpoint age before deleting D1 rows. Active checkpoints survive cleanup races. Idle object copies expire after a day. Account deletion purges object copies before deleting snapshot/thread rows; a missing cleanup binding defers deletion rather than claiming success. Ordinary saved issue content remains.

## Optional Worker setup

This local build does not enable or deploy the feature. Migration `0043_editor_collaboration.sql` is generated and unapplied. No provider, DNS or production settings were changed. Existing deployment bindings stay unchanged until the operator opts in.

1. Apply the new D1 schema in each intended region during an approved release.
2. Deploy the API Worker with its named `CollaborationAuthority` entrypoint, then deploy `workers/collaboration/wrangler.jsonc` (and `--env eu`). The new Worker binds `AUTHORITY` to the matching regional API entrypoint and owns the SQLite `CampaignRoom` class. No public custom domain or workers.dev address is needed.
3. Add an optional `COLLABORATION_SOCKET` service binding to the regional app Worker and router, targeting the matching collaboration Worker's default entrypoint. Add `COLLABORATION_STORAGE` to the app and API Worker, targeting its named `CollaborationStorage` entrypoint. These service bindings are internal, never public HTTP identity endpoints. For a self-hosted Worker use its own matching service names and configured `APP_URL`.
4. Enable `COLLABORATION_ENABLED=true` on the app, API and collaboration Workers. Set the collaboration Worker's `APP_URL` to the exact canonical dashboard origin. Keep it false until bindings, cleanup and actual browser QA pass. Each region remains independent. Bootstrap these optional bindings only after the target Workers exist; do not add missing service targets to a normal deployment.
5. Verify two browser sessions editing the same rich draft, offline/reconnect, cursors, private anchor navigation/mentions, outside REST edit/restore, scheduled/send locking, session/team revocation, export and actual account/object cleanup. Repeat in the EU namespace. Native local tests do not prove deployed topology or browser UX.

Build with `npm run build:collaboration`. `npm run test:collaboration` runs the separate Cloudflare/Vitest native suite; keep `npm test` for the app. The optional DOM parser uses Linkedom's bundled CSSOM implementation; its unused optional cssstyle override is disabled at build time so Workers never try a dynamic package lookup. The build fails if that dependency hook changes and needs review. The new Vitest plugin's pinned Zod is overridden to the existing patched 4.6.6 line; no broad audit fix was run.

Current official references: [Cloudflare WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [jurisdictions](https://developers.cloudflare.com/durable-objects/reference/data-location/), [native tests](https://developers.cloudflare.com/workers/testing/vitest-integration/write-your-first-test/), [Tiptap collaboration](https://tiptap.dev/docs/editor/extensions/functionality/collaboration).

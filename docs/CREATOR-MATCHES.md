# Creator matches and private introductions

On `/recommending/creators`, a creator can opt a newsletter into topic and subscriber-range matching. The newsletter must already be listed for recommendations and pass the same current signup checks: website, confirmation, sender, first issue and account availability. Matching never enables a public directory listing on its own. Both matching and email notifications default off. Each regional database is independent; there is no cross-region lookup.

Up to 50 suggestions are ranked from a stable window of 200 eligible candidate profiles. Each shared topic adds 10 points, a shared subscriber range 3, and language 2. An active outgoing recommendation adds up to 5 points from your own confirmed signup count. These are transparent sorting rules, not a forecast of subscribers or swap performance. Results say when the window or result limit is incomplete. The only recommendation counts included are the requesting newsletter's own outgoing recommendation records. Exact audience counts, subscriber records, account IDs and private email addresses are never returned. Topics are normalized and deduplicated, with up to ten of 2–30 characters each.

An introduction sends the creator's own words to a private inbox; it does not add a recommendation, create a swap obligation, subscribe a contact or schedule anything. There is one account-scoped conversation and message copy per participant. Docdb inserts both message copies in one transactional call. A stable external ID makes retries return the same acceptance; reusing it with different text or another recipient is refused. Retrying repairs inbox ordering after an interrupted response without recreating a deleted account's copy. Conversation setup can leave an empty row after a failure; empty rows do not appear in the inbox.

New introduction attempts are limited to three per account per day; replies to 30 per hour. API action limits and agent daily caps also apply. Limits use the existing Redis service, or the existing process-memory fallback when Redis is absent; the fallback is not a global distributed quota. Concurrent duplicate attempts may consume additional limiter slots even though they produce one message. Existing conversations continue after either matching profile is switched off. Either participant can close its side; the other participant cannot reopen it. Closure is checked before acceptance, and cannot recall an already accepted or in-flight message. Both accounts must remain available to accept new messages.

If the recipient explicitly enables email notifications, the account owner may receive the message text from FlockStack's platform sender, with a link to the authenticated conversation. No account address is supplied as the sender or reply-to. Names and anything the sender deliberately writes are part of the message. At most one notification is attempted per conversation per hour. Platform sending configuration and `SENDING_ENABLED` apply. Notification failures never turn a saved inbox message into a claim of email delivery. An attempt is marked before sending; a process interruption can miss that email notification. The inbox is the record.

The dashboard, REST and MCP use the same eight actions. Introduction and reply actions have the `send` class; agent approval settings, presets, newsletter limits, daily caps and team permissions apply before any message is sent. The activity log keeps IDs and counts, not message text. All output is plain text and the dashboard renders it as escaped text. Private message reads are recorded in agent activity.

Conversation and message lists use bounded cursor pages of 50. Private account exports include creator profile settings, `creator-conversations.csv` and `creator-messages.csv`, scoped to that account. Account purge removes its copies; the other participant retains its own copy. No public inbox or message search endpoint exists. Migration `0037_creator_matches.sql` creates the two account-scoped tables and indexes; it has not been applied to production by this local build.

The `creator_message.created` webhook carries only the message ID, newsletter ID and conversation ID (`parentId`) for each owning account. Emission is best effort through the existing webhook delivery queue, claimed once per message copy; a retry does not duplicate its notification. No private text is placed in webhook data or agent summaries, even when the text resembles an ID. Zapier and Make event definitions are updated locally; no connector has been submitted or published.
